Phần 1 - Phân tích logic: POST vs PUT và tính Idempotent

1. Sự khác biệt bản chất giữa HTTP POST và HTTP PUT
Mục đích sử dụng:

HTTP POST: Được thiết kế để tạo ra một tài nguyên mới nằm dưới quyền quản lý của một URL cha (Collection). Khi dùng POST, phía Server thường là bên chịu trách nhiệm tự sinh ra ID cho đối tượng đó.

HTTP PUT: Được thiết kế để cập nhật một tài nguyên đã biết trước định danh (ID) hoặc thay thế hoàn toàn tài nguyên cũ tại một URL cụ thể.

Đường dẫn định danh (URI):

HTTP POST: Thường trỏ đến một tập hợp chung chung. Ví dụ: /api/customers (Ý nghĩa: "Thêm một khách hàng mới vào danh sách này").

HTTP PUT: Trỏ trực tiếp đến một phần tử cụ thể đã có ID rõ ràng. Ví dụ: /api/customers/1 (Ý nghĩa: "Hãy ghi đè thông tin mới vào đúng vị trí của khách hàng có ID là 1").

Tính chất Idempotent (Tính lặp lại):

HTTP POST không có tính Idempotent: Nghĩa là nếu bạn gửi 10 yêu cầu POST giống hệt nhau lên hệ thống, Server sẽ hiểu đó là 10 yêu cầu tạo mới riêng biệt và sẽ sinh ra 10 bản ghi khách hàng trùng lặp nhau trong cơ sở dữ liệu.

HTTP PUT có tính Idempotent: Nghĩa là dù bạn có bấm gửi yêu cầu cập nhật đó 1 lần hay 100 lần đi chăng nữa, trạng thái cuối cùng của tài nguyên trên hệ thống vẫn duy nhất và như nhau, không hề phát sinh thêm bản ghi rác.

2. Nguyên nhân mã nguồn cũ gây lỗi dữ liệu
Khi bạn gom cả hai hành vi tạo mới và cập nhật vào chung một endpoint @PostMapping("/api/customers"), hệ thống đã gặp hai lỗi logic nghiêm trọng:

Mất tính Idempotent khi người dùng cập nhật nhanh: Khi người dùng nhấn nút "Cập nhật" liên tục do mạng lag, các request POST song song được gửi lên. Do mạng chập chờn, có thể request đầu tiên chưa xử lý xong (ID chưa kịp sinh ra hoặc chưa kịp phản hồi về), các request tiếp theo gửi lên vẫn có id == null. Hệ thống lập tức coi đó là các yêu cầu tạo mới và tiếp tục sinh thêm các ID khác, dẫn đến trùng lặp dữ liệu của cùng một người dùng.

Tự ý tạo mới ở nhánh xử lý lỗi: Trong khối else cuối cùng, logic cũ quy định rằng nếu Client truyền lên một ID nhưng hệ thống tìm trong danh sách không thấy (có thể do ID sai hoặc tài khoản chưa được đồng bộ), thay vì trả về lỗi, hệ thống lại tự ý dùng lệnh customers.add(customer) để ép thêm bản ghi đó vào danh sách. Điều này vi phạm quy tắc bảo mật dữ liệu của ngân hàng, nơi mà ID phải luôn được kiểm soát chặt chẽ.

Phần 2 - Thực thi: Tách biệt và Chuẩn hóa API



Java
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.util.ArrayList;
import java.util.List;
import java.util.Optional;
import java.util.concurrent.atomic.AtomicLong;

@RestController
@RequestMapping("/api/customers")
public class CustomerController {
    private List<Customer> customers = new ArrayList<>();
    private AtomicLong nextId = new AtomicLong(1);

    static class Customer {
        private Long id;
        private String name;
        private String email;

        public Customer() {}
        public Customer(Long id, String name, String email) {
            this.id = id;
            this.name = name;
            this.email = email;
        }

        public Long getId() { return id; }
        public void setId(Long id) { this.id = id; }
        public String getName() { return name; }
        public void setName(String name) { this.name = name; }
        public String getEmail() { return email; }
        public void setEmail(String email) { this.email = email; }
    }

    /**
     * API 1: Tạo mới một khách hàng
     * Endpoint định chuẩn: POST /api/customers
     */
    @PostMapping
    public ResponseEntity<Customer> createCustomer(@RequestBody Customer customer) {
        // Luôn để hệ thống tự cấp phát ID khi tạo mới nhằm tránh xung đột dữ liệu
        customer.setId(nextId.getAndIncrement());
        customers.add(customer);

        return new ResponseEntity<>(customer, HttpStatus.CREATED);
    }

    /**
     * API 2: Cập nhật thông tin khách hàng hiện có
     * Endpoint định chuẩn: PUT /api/customers/{id}
     */
    @PutMapping("/{id}")
    public ResponseEntity<Customer> updateCustomer(@PathVariable Long id, @RequestBody Customer updatedData) {
        // Định vị chính xác khách hàng cần sửa đổi dựa trên ID lấy từ đường dẫn URL
        Optional<Customer> existingCustomer = customers.stream()
                .filter(c -> c.getId().equals(id))
                .findFirst();

        if (existingCustomer.isPresent()) {
            Customer currentCustomer = existingCustomer.get();
            // Thực hiện ghi đè dữ liệu mới lên bản ghi cũ
            currentCustomer.setName(updatedData.getName());
            currentCustomer.setEmail(updatedData.getEmail());

            // Trả về kết quả thành công với mã 200 OK
            return new ResponseEntity<>(currentCustomer, HttpStatus.OK);
        } else {
            // Nghiệp vụ yêu cầu không tự ý tạo mới nếu không tìm thấy dữ liệu.
            // Trả về mã trạng thái lỗi hệ thống 404 Not Found để thông báo cho Client.
            return new ResponseEntity<>(HttpStatus.NOT_FOUND);
        }
    }

    @GetMapping("/{id}")
    public ResponseEntity<Customer> getCustomerById(@PathVariable Long id) {
        return customers.stream()
                .filter(c -> c.getId().equals(id))
                .findFirst()
                .map(c -> new ResponseEntity<>(c, HttpStatus.OK))
                .orElse(new ResponseEntity<>(HttpStatus.NOT_FOUND));
    }
}
